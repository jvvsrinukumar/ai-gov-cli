Overview

What ai-gov is

A CLI tool that generates governance scaffolding for AI coding agents (Claude Code and Kiro). Running npx ai-gov init in a project detects the stack and produces ~40 files — steering documents, IDE hooks, slash commands, spec templates — that give the AI agent consistent architectural context.

It supports 9 stacks (Flutter, Kotlin, React, Next.js, Angular, Node.js, Python, Java, SwiftUI) and targets team-level consistency — preventing five developers using Claude Code on the same codebase from getting five different architectures generated at machine speed.

How it works in practice

The framework operates at four levels simultaneously — always-loaded steering context, automatic hooks on every tool use, git commit guards, and CI PR checks. Understanding which role belongs to which level is key to using it correctly.

The 5 steering files — always loaded by the AI

constitution.md
Hard rules, architecture invariants, high-risk files. Also: project domain context (healthcare/fintech/general) and data security rules (PHI/PII/general + per-stack additions). Highest priority — never violated.
architecture.md
Layer flow, patterns, external service boundaries, data layer patterns (ORM-specific migration rules), naming conventions by layer and directory. The AI reads this before any architectural decision.
coding-standards.md
Naming rules, type naming, error handling, file size limits (200 lines for frontend), import order. Stack-specific test conventions: MockK (Kotlin), Jest/NestJS (Node.js), React Testing Library (React), pytest (Python), JUnit 5 (Java).
workflow.md
Feature/fix/refactor/hotfix flows, commands table, AI usage policy (prerequisites, forbidden actions), spec-first workflow with STOP gates and completeness criteria.
developer-reference.md
Feature README template, prompt templates for each task type, task size/time estimate markers ([~1h], [S/M/L]) used by the /jira command.

What it does well

Genuine strengths

🎯
The problem is real and clearly articulated
▴
Five developers using Claude Code on the same codebase without shared rules produces chaos at machine speed. The framework addresses this directly — not with documentation, but with mechanical enforcement via hooks, steering context, and spec gates.
🔍
Comprehensive stack coverage and detection logic
▾
9 stacks with detailed per-stack profiles — layer flows, commands, naming conventions, scanners that auto-detect state management, DI, ORM, routers, package managers. Detection handles monorepos, sub-modules, multi-module Maven/Gradle, Kotlin vs Java disambiguation, NestJS vs Express vs Fastify subtypes.
⚡
Well-designed command pipeline with persistent output
▾
/tech-knowledge → /product-knowledge → /audit → /assess → /backlog → /new-feature is a coherent workflow. Each command is self-contained, produces git-committed output that feeds the next, and uses completion contracts (grep-able terminal lines) for mechanical verification.
🛡️
Hook system is practical — high value, zero developer overhead
▾
PreToolUse hooks that block secrets, enforce spec-first, and prevent dangerous shell commands are the kind of guardrails teams actually need. They work mechanically — they don't depend on AI judgement. That's their value. The exit-code protocol (0=allow, 2=block) is clean. Hooks fire automatically; developers don't have to remember anything.
🧠
Knowledge hub solves the AI memory problem correctly
▾
AI agents have no memory across sessions. The knowledge hub breaks the reset cycle: git-committed files that grow as a byproduct of Gate 1 approvals, with drift detection (/audit) and conflict surfacing (/detect-conflicts). The [INFERRED] / [CONFIRMED] confidence model is well-reasoned — AI extracts, humans verify, git tracks history.
🧪
Strong test coverage — 1704 tests across 50 suites
▾
Test suite covers scanners, generators, CLI integration, state migration, PR checks, Kiro hooks, knowledge commands, and property-based tests (fast-check). For a code generator producing AI context files, this level of coverage is genuinely solid. The generator tests catch regressions before teams see broken steering files.
📋
Honest about limitations — stated in README
▾
"Not worth it for solo dev prototyping" and "Steering gives a better starting point, not absolute control" appear directly in the README. This honesty is not common in developer tooling and builds trust with teams evaluating adoption. The framework doesn't oversell what prompt-based governance can guarantee.
Concerns and responses

Concerns & responses

An independent assessment raised several concerns. Here is each concern alongside the team's reasoning and response.

⚠️
1. Complexity vs. adoption barrier — ~40 files, hooks, steering, knowledge
▾
The framework generates ~40 files and has significant cognitive overhead. There is no "light mode." A team wanting only hooks or only steering has to understand the whole system to know what is safe to remove.
Response
The plan is to make this the standard way the team works with AI agents. If governance is the norm, the complexity is a one-time team setup cost — not per-developer friction. The CLI abstracts it: one command, one init, done. A developer doesn't need to understand all 40 files any more than they need to understand webpack to run npm run build.
⚠️
2. Spec-first enforcement is heavy-handed — blocks all writes without a complete spec
▾
check-spec-exists blocks all file writes if a complete spec doesn't exist. For teams with existing features that predate the framework, every un-specced directory becomes un-editable until a retroactive spec is created.
Response
This is intentional — it is an equalizer. AI agents generate code at machine speed. Without this gate, a junior developer asking Claude for a feature gets untethered architecture in 30 seconds. The spec gate forces human thought before machine execution. Junior or senior, everyone follows the same flow. That is the concept: not friction, but discipline. Existing unspecced features are addressed at onboarding by creating retroactive specs — which also documents what already exists, a net gain.
⚠️
3. Steering assumes the project matches the detected stack perfectly
▾
For non-standard projects — Next.js with a custom backend, React inside a monorepo with shared packages — the scanner can be significantly wrong and the generated steering won't reflect reality.
Response
Scanner stays simple; /audit fills the gap. Keeping scanners lean is a deliberate tradeoff — complex heuristics create complex bugs. The scanner gets you 80% correct on day one. /audit reads the actual live codebase and corrects what the scanner got wrong. If a new pattern appears at the stack's core level, audit detects the drift. Division: scanner = initial approximation, audit = ground truth verified against real code.
⚠️
4. Commands are enormously long prompt documents — context cost and fragility
▾
/audit is ~500 lines of instructions. /assess and /backlog are similar. These consume significant context window and are fragile — if the AI deviates from rigid formatting requirements or context fills mid-command, the run produces incomplete output with no recovery other than starting over.
Response
These are periodic team-lead tools, not daily developer commands. /audit, /assess, and /backlog are run at release checkpoints or sprint boundaries — not in the daily development flow. Daily commands (/fix, /new-feature, /explore) are significantly shorter. The long commands produce structured batch reports used for team planning — the context cost is acceptable at that cadence.
⚠️
5. Knowledge capture is ambitious but brittle — depends on AI correctly classifying every fix
▾
Silent knowledge capture depends on the AI correctly distinguishing "technical fix" from "business rule fix" every single time. False positives pollute the knowledge base; false negatives lose institutional memory. There is no easy audit trail for what was captured.
Response
Knowledge commands are a release cadence activity — not silent background drift. The team lead runs /tech-knowledge and /product-knowledge explicitly before each release. This checkpoint, followed by /audit to validate health, prevents silent drift. Knowledge isn't passively accumulating unreviewed — it is actively regenerated and verified at known points in the release cycle.
⚠️
6. No runtime validation — AI can drift from steering in subtle ways
▾
The framework validates at generation time and commit time, but there is no mechanism to verify the AI actually followed steering during a session. A developer could bypass git hooks and the AI could put logic in the wrong layer without triggering the architecture hook.
Response
Correct — and stated openly in the README. The framework gives a better starting point, not absolute control. Steering is context, not a constraint system. /audit catches architectural drift after the fact. A developer who deliberately runs --no-verify has made a conscious choice. Governance cannot prevent deliberate circumvention — it can only make it visible and raise the cost of bypassing.
⚠️
7. Single-author bus factor — concentrated ownership risk
▾
One person authored the package. For a governance tool that teams depend on, concentrated ownership is a real dependency risk.
Response
Valid concern for production dependency — honest to name it. For internal team use this is manageable. The architecture (pure generators, zero runtime dependencies, clean TypeScript) makes it straightforward to fork or extend. A CONTRIBUTING guide exists. For broader external adoption, this is a people-and-process problem that needs addressed over time — not a technical one.

⚠️
Known detection issue: The framework's own governance-state.json declares it as a "React" project because "react" appears in its keywords field and the scanner matches against the full package.json text. The framework is actually a Node.js CLI tool. This is a cosmetic false positive that affects only the framework's self-governance — not any project it governs. Fix: scope detector to dependencies/devDependencies only. Tracked for next release.
For teams of 3+ developers using Claude Code or Kiro on production codebases
The hooks alone — secrets guard, dangerous command block, spec-first gate — provide immediate, mechanical value on day one without any workflow change
The knowledge hub solves the AI memory problem correctly: git-committed, auto-growing, drift-detected, verified before each release
Zero-knowledge developer onboarding: a developer with no backend experience opens one file and finds everything needed to get from git clone to a running server with a connected database
The spec-first gate is an equalizer — junior or senior, AI generates only after a human has reviewed requirements, design, and task breakdown
The upgrade path is safe and explicit: ai-gov upgrade --force writes new files first, then deletes retired files — specs, knowledge, and custom content are never touched
The honest remaining limitation: the framework is a discipline multiplier, not a discipline substitute. A team lead who runs knowledge commands and audit before each release gets compounding returns — every sprint the knowledge base gets more accurate and code generation gets more contextually correct. A team that installs it and never runs audit will see hooks fire but miss the knowledge and drift-detection benefits entirely.
