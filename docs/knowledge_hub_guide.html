01

What is the Knowledge Hub

The Knowledge Hub is a persistent, git-committed intelligence layer that sits between your codebase and your AI agent. It solves one specific problem: AI agents have no memory across sessions. Every /fix or /new-feature starts from zero — the agent re-reads the same files, re-infers the same patterns, and sometimes draws different conclusions.

The Knowledge Hub breaks that reset cycle. Knowledge files are committed to git, read automatically by every developer command, and grow as a byproduct of normal sprint work — without anyone writing documentation.

02

Confidence Model

✅
All tags are read — the tag controls trust level, not whether the file is used. A knowledge file with only [INFERRED] entries (e.g. right after bootstrapping) is still loaded and provides valuable context.
[INFERRED]
AI extracted from code — not human-verified. Still read and used by all commands. AI verifies against actual code before acting. If code contradicts the entry, the discrepancy is noted.
[CONFIRMED]
Human-verified via Gate 1 approval or manual edit. Trust fully. Never overwritten by AI. Protected by pre-commit guard — removal requires env-var bypass.
[UNKNOWN]
Observable but not understood. Requires human input. Flag for team discussion. Do not rely on for code generation.
[STALE] — audit only
Code contradicts the entry — the thing changed or was removed. Re-run /tech-knowledge or /product-knowledge for that scope.
[UNVERIFIABLE] — audit only
No code found to verify the entry — may be deleted or moved. Human review required.

Merge rules — what happens at Gate 1 approval

  • [CONFIRMED] entries → never overwritten. Only a human can change them.
  • [INFERRED] entry that requirements confirm → upgraded to [CONFIRMED]
  • [INFERRED] entry requirements don't address → left unchanged
  • New entries from requirements not in file → appended as [CONFIRMED]

The spec-first workflow. No files are written until Gate 3 is approved. Knowledge is read before Gate 1 and written automatically after Gate 1.

  • Data flow + error handling strategy
  • Developer says: ok
No knowledge capture — design is structural, not business rules. No files written.

  • Phase breakdown shown in chat (Phase 1 Domain → Phase 5 Tests)
  • Developer says: ok

Product knowledge already captured at Gate 1 — no further action. Tech knowledge unchanged (new feature follows existing patterns).

What gets captured at Gate 1

  • Domain Objects — entities or data types explicitly named
  • Permissions & Roles — any role or access rule stated

06

Edit Feature

Same 3-gate flow as /new-feature with one critical difference in silent capture.

  • Knowledge preamble reads existing knowledge for that scope — same as new-feature
  • Gate 1 shows a diff view — changed items marked <!-- NEW --> or <!-- CHANGED: ... -->
  • Silent capture fires after Gate 1 — but only extracts from marked items
  • Does not re-capture unchanged requirements already in the knowledge file
  • Gate 2 and Gate 3 — identical to new-feature
⚠️
If Gate 1 requirements have no <!-- NEW --> or <!-- CHANGED --> markers, capture outputs: ↳ Knowledge capture: no extractable entries in requirements.

Knowledge preamble reads first — the AI knows the documented intended behaviour before diagnosing. If a [CONFIRMED] entry says "notifications are user-scoped — never leak across users" and the bug is about data leaking, the AI flags the connection immediately.

08

Refactor

Preamble reads knowledge/tech-[slug].md specifically — the AI knows the existing layer structure before proposing changes. Refactor proposals stay consistent with documented architecture.

  • Preamble reads: knowledge/tech-[slug].md (HOW the code is built)
  • No silent capture — refactors change structure, not business rules
  • After refactor: knowledge/tech-[slug].md may become stale — /audit catches this at the next release audit. Team lead re-runs /tech-knowledge [scope] to refresh.
  • Team lead action: re-run /tech-knowledge [scope] to refresh

✅

Tech knowledge only goes stale on structural changes — new ORM, new architectural layer, new auth approach. Routine features that follow existing patterns do not require a re-run.
10

Release Audit

The team lead runs /audit at two points: before every push after knowledge commands (bootstrap and release prep), and whenever something seems broken. It is not a passive weekly check — it is an active quality gate that must pass before code reaches the repo.

🚨
Rule: knowledge commands → /audit → commit + push. Never commit knowledge files without running /audit first. A stale or unverifiable entry committed to the repo will be read as fact by every developer's /new-feature and /fix for the rest of the sprint.

Team lead checklist — before every release

StepActionWhy
1Identify scopes that changed this releaseOnly re-run knowledge for scopes with significant structural changes — new ORM, new layer, new auth approach
2/tech-knowledge [changed-scope]Refreshes HOW file for changed scopes
3/product-knowledge [changed-scope]Refreshes WHAT file — only if business rules or flows changed significantly; Gate 1 captures handle most updates automatically
4/auditValidates all knowledge entries against live code. Must show zero stale, zero unverifiable before proceeding
5Fix any stale/unverifiable entries flaggedRe-run /tech-knowledge [scope] for each flagged file → /audit again
6/detect-conflictsSurfaces contradicting business rules across features — generates decision inbox in knowledge/conflicts/
7Resolve open conflictsEdit conflict files, mark decisions, commit
8git add knowledge/ && git commit && git pushOnly after audit shows all current
9Tag the releaseKnowledge is clean — all commands have accurate context for next sprint

These files are automatically available to the AI in every session via CLAUDE.md. They define the rules the AI must not violate when generating code.

FileContainsWhen read

Layer 2 — Hooks (fire automatically on every file write)

Hooks are shell scripts or Kiro hook files that the framework installs into .claude/hooks/ or .kiro/hooks/. They fire automatically — the developer sees the output inline, no extra command needed.

HookFires whenWhat it does
spec-first-gateAny file write attemptBlocks code generation if no Gate 3-approved spec exists. Enforces spec-first — no code before spec.
pre-write-secrets-gateBefore writing any fileScans the content about to be written for credential patterns. Blocks the write if secrets detected.
format-codeAfter each file writeRuns the stack's formatter (prettier, ruff format, dart format, spotless) on the written file.
analyze-codeAfter each file writeRuns the stack's linter (eslint, ruff check, dart analyze, checkstyle) on the written file.
check-file-sizeAfter each file writeWarns if the file exceeds 200 lines (configurable). Flags for refactoring before it becomes a problem.
check-secretsAfter each file writePost-write scan for accidentally included credentials, tokens, or PII.
check-feature-readmeAfter feature folder createdReminds the developer to write a README for the new feature. Not a blocker — a nudge.
check-consistencyAfter each file writeChecks naming conventions match what's documented in CLAUDE.md and coding-standards.md.
post-task-checklist (Kiro)After each task completedVerifies: architecture compliance, no skipped layers, tests written, file size, tasks.md updated, Jira reminder.
💡
All hooks are installed by ai-gov init and fire without developer action. The developer sees the output inline in the chat or panel. If a hook flags an issue, the AI resolves it before moving to the next file.

Layer 3 — Git Hooks (fire at git commit)

ai-gov init --git-hooks installs wrappers in .git/hooks/ that call the governance checks at commit time.

HookFires whenChecks run

check-file-size.sh — warns on files exceeding the line limit
.git/hooks/commit-msg Every git commit Enforces commit message format — must include ticket prefix or conventional commit type. Blocks commit if format violated.
