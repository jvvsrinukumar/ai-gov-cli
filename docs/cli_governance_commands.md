## Why Commands Instead of Prompt Templates

Before v14.3, governance relied on developers writing the correct `## Task Type:` header in every prompt. This was developer-dependent — someone could ignore it, forget it, or phrase a task differently and bypass the entire governance workflow.

v14.3 replaces that with **slash commands**. Each command is a pre-loaded workflow that Claude executes exactly — no template to remember, no discipline required. The `require-task-type.sh` hook intercepts freeform task requests and reminds developers to use the correct command.

**Old approach (prompt-dependent):**
```
## Task Type: New Feature
## Feature: user_profile
Build a user profile screen...
```

**New approach (command-driven):**
```
/new-feature user_profile
```

Claude enters plan mode, runs the 3-gate spec approval, and only writes files after explicit developer approval. No template needed. No discipline required.

## The 6 Governance Commands

Generated by `ai-gov init` into `.claude/commands/`. Available immediately after running `claude` in a governed project.

All 6 commands use plan mode. Nothing is written until the developer explicitly approves at the gate.

| Command | Plan Mode | Gates | Purpose |
|---|---|---|---|
| `/new-feature [name]` | YES | 3 (requirements → design → tasks) | Build something new with full spec |
| `/edit-feature [name]` | YES | 3 (updated spec, preserves existing) | Add to or change an existing feature |
| `/explore [scope]` | YES | 1 (choose next action after reading) | Understand code first — then create spec, update spec, fix, or refactor |
| `/fix [description]` | YES | 1 (root cause + proposed fix) | Fix broken behaviour |
| `/refactor [scope]` | YES | 1 (impact analysis — tests run after gate) | Structural improvement, no behaviour change |
| `/hotfix [issue]` | YES | 1 (emergency diagnosis — lightweight) | Production issue — fast diagnosis then immediate fix |

## /new-feature — Full Detail

### What It Does

Enters plan mode immediately. Shows each spec document as a text preview in the chat — no files written. Developer reviews and approves each document. After all 3 approvals, plan mode exits and spec files are written. Developer then selects which phases to implement.

### The 3-Gate Approval Flow

```
/new-feature order-management
        ↓
[Plan Mode Starts — Claude cannot write any files]
        ↓
─── GATE 1: Requirements ─────────────────────────────────────
Claude shows requirements.md content as markdown in chat:
  • Feature overview (1-2 sentences)
  • Acceptance criteria (checkboxes)
  • API contracts (method/endpoint/purpose table)
  • Out of scope (explicit list)

Developer reviews. Can request changes — Claude updates and shows again.
✓ "ok" / "approved" / "looks good" / "lgtm" → advance to Gate 2
──────────────────────────────────────────────────────────────
        ↓
─── GATE 2: Design ───────────────────────────────────────────
Claude shows design.md content as markdown in chat:
  • Architecture layer map (table: layer / files / responsibility)
  • Data flow through layers
  • State shape (if applicable)
  • Error handling strategy
  • Dependencies on existing features/services

✓ Developer approves → advance to Gate 3
──────────────────────────────────────────────────────────────
        ↓
─── GATE 3: Tasks ────────────────────────────────────────────
Claude shows tasks.md content with full phase breakdown:
  • Phase 1 through Phase 5 (stack-specific — see table below)
  • Specific files per phase
  • Definition of Done checklist

✓ Developer approves → plan mode ends
──────────────────────────────────────────────────────────────
        ↓
[Plan Mode Ends — ExitPlanMode called]
        ↓
Claude writes:
  specs/order-management/requirements.md
  specs/order-management/design.md
  specs/order-management/tasks.md
        ↓
"Which phases to implement? all / phase 1 / phase 1 and 2 / spec only"
        ↓
Developer chooses → Claude implements ONLY those phases
```

### Phase-Selective Implementation

After spec files are written, the developer controls exactly what gets coded:

| Developer says | Claude implements |
|---|---|
| `all` or `develop` | All 5 phases in order |
| `phase 1` | Phase 1 only, then stops |
| `phase 1 and 2` | Phases 1 and 2, then stops |
| `phase 1 2 3` | First three phases, then stops |
| `spec only` | Stops — implement later |

After each phase, Claude updates `tasks.md` (marks done tasks `[x]`) and shows a summary. The next session can resume from the first unchecked task.

## /edit-feature — Full Detail

### What It Does

For adding to or changing a feature that already exists. Same 3-gate plan mode flow as `/new-feature`, but starts by reading the existing spec files first.

### How It Differs from /new-feature

| Behaviour | /new-feature | /edit-feature |
|---|---|---|
| Reads existing spec first | No | Yes — reads all 3 existing files |
| Shows spec content | Full draft | Updated content (existing + additions marked `<!-- NEW -->`) |
| Existing checked tasks | N/A | Preserved exactly as `[x]` |
| Existing pending tasks | N/A | Preserved exactly as `[ ]` |
| New tasks | All tasks | Added at bottom of relevant phase |

### What "Preserved" Means

If `tasks.md` currently has:
```
- [x] Create domain entity        (done)
- [x] Create repository impl      (done)
- [ ] Create BLoC cubit            (pending)
```

After `/edit-feature`, the output will be:
```
- [x] Create domain entity        (unchanged)
- [x] Create repository impl      (unchanged)
- [ ] Create BLoC cubit            (unchanged)
- [ ] Add password change modal   <!-- NEW -->
- [ ] Add password validation     <!-- NEW -->
```

Existing progress is never lost.

## /explore — Full Detail

### What It Does

Read and map a feature or module in plan mode before deciding what to do. Use when you need to understand existing code before fixing, speccing, or refactoring it. After reading, the developer chooses the next action — the files are already loaded, no re-reading needed.

### Flow

```
/explore nft-feature
        ↓
[Plan Mode Starts]
        ↓
Step 2: Read all files in scope
  source files (all layers), specs/ (if exists), tests/, README
        ↓
Step 3: Code Map
  Layer structure, data flow, patterns, file sizes, dependencies
        ↓
Step 4: Findings
  Spec: MISSING / EXISTS / STALE
  Tests: SCENARIO A / B / C
  Issues noticed while reading
  Architecture match vs steering
        ↓
Step 5: Next Action Gate
  create spec  → if spec is MISSING (reverse spec from observed code)
  update spec  → if spec is STALE
  fix [desc]   → bug found — files already loaded, straight to root cause
  refactor     → structural issue — impact table ready, straight to gate
  done         → context acquired, no changes
        ↓
[ExitPlanMode on developer choice]
```

### The "create spec" case — reverse spec

This is distinct from `/new-feature`. The code already exists — the spec documents reality:

| `/new-feature` | `create spec` from `/explore` |
|---|---|
| Designs something new | Documents what already exists |
| Requirements: what SHOULD it do | Requirements: what DOES it do |
| Design: planned architecture | Design: observed layers and data flow |
| Tasks: what to build | Tasks: what to clean up / test |
| Claude uses imagination | Claude uses what it just read |

### Seamless transitions (no re-reading)

When the developer says `fix` or `refactor` after exploring, Claude transitions directly into that command's flow using the files already loaded in Step 2. No repeated reads.

## /fix — Full Detail

### What It Does

Read and diagnose in plan mode. One gate — developer sees root cause and proposed fix before any file changes. Minimum change only.

### Flow

```
/fix login-spinner-never-stops
        ↓
[Plan Mode Starts]
        ↓
Step 2: Read relevant files
        ↓
Step 3: Scope check
  ≤ 3 files → proceed
  > 3 files → flag scope warning
        ↓
━━━ ROOT CAUSE ━━━ + ━━━ PROPOSED FIX ━━━  (THE GATE)
  "Root cause: AuthCubit.login() emits AuthLoading() but never
   emits AuthFailure() when token response is null — spinner hangs"
  "Fix: add null check, emit AuthFailure('Session expired')"
  Say apply — or redirect to /refactor / /new-feature / /hotfix
        ↓
Developer: "apply"
        ↓
[ExitPlanMode]
        ↓
Step 5: Apply fix — minimum change only
        ↓
Step 6: Verify + run tests
```

### Redirect options at the gate

| Developer says | What happens |
|---|---|
| `apply` | ExitPlanMode → fix applied |
| `/refactor` | This is structural — reclassify |
| `/new-feature` | Capability is missing — reclassify |
| `/hotfix` | Production emergency — reclassify |
| `stop` | Cancel |

## /refactor — Full Detail

### What It Does

Read and map impact in plan mode. One gate — developer approves the file list before anything changes. Tests run immediately after the gate, before refactoring begins.

### Flow

```
/refactor extract-validation-into-service
        ↓
[Plan Mode Starts]
        ↓
Step 2: Read all files in scope
        ↓
━━━ IMPACT ANALYSIS ━━━  (THE GATE)
  Files that WILL change: [table with current → after]
  Files that will NOT change: [callers, dependents]
  Behaviour change: None
  Test risk: low/medium
  Say approved — or redirect to /fix / /hotfix
        ↓
Developer: "approved"
        ↓
[ExitPlanMode]
        ↓
Step 4: Run tests BEFORE refactoring
  If failing → stop, fix first (/fix), then refactor
        ↓
Step 5: Apply refactor file by file
        ↓
Step 6: Run tests AFTER — must pass before closing
```

### Hard Rules

- If a bug is found during refactoring: note it, do not fix it (create a `/fix` task)
- If scope expands unexpectedly: stop and report before continuing
- No feature additions during refactor

## /hotfix — Full Detail

### What It Does

Fast diagnosis in plan mode. One lightweight gate — developer sees Issue / Root cause / Fix / Risk before the fix is applied. The gate is a diagnosis display, not a planning session. Fix then mandatory post-fix summary.

### Flow

```
/hotfix eu-payments-500-since-2.3.1
        ↓
[Plan Mode Starts — max 5 files read]
        ↓
━━━ EMERGENCY DIAGNOSIS ━━━  (THE GATE)
  Issue:      EU payments returning 500 since deploy 2h ago
  Root cause: connectionTimeout set to 0ms in connection.js:47
  Fix:        Restore to 5000ms — 1 line change
  Risk:       Low — config only, no logic change

  This is a diagnosis display — not a planning session.
  Say apply to proceed immediately.
        ↓
Developer: "apply"
        ↓
[ExitPlanMode]
        ↓
Step 3: Apply fix — minimum change only
        ↓
Step 4: Run tests / verify manually
        ↓
Step 5: Post-fix summary (REQUIRED — always output this)
  "HOTFIX SUMMARY — Requires Review
   Fix applied: connection.js:47 — timeout restored to 5000ms
   Follow-up: code review · add config test · monitor EU payment rate"
```

### Hard Rules

- If > 5 files need changing: not a hotfix — stop and reclassify as `/refactor`
- Post-fix summary block is never optional
- Hotfixes bypass spec-first workflow and must be reviewed after deploy

## /audit — Project Health Check

```
/audit
```

12-step project truth check. Not a task type — a governance verification tool.

**When to run:**
- Start of every sprint
- After `ai-gov init` (confirm scanner picked up right stack)
- After major refactor
- When onboarding a new developer
- When Claude seems to be misbehaving (stale steering)

**What it returns:**

```

────────────────────────────────────────────
```

## require-task-type Hook — The Classification Gate

### What It Does

Fires on every user message (`UserPromptSubmit`) before Claude processes it. Detects development task requests that don't use a governance command or `## Task Type:` header, and shows a reminder.

### What It Catches

```
Developer types: "build a notification feature"
        ↓
Hook detects: "build" + "feature" keyword → no /command, no ## Task Type
        ↓
Claude receives additionalContext:
  "GOVERNANCE: This looks like a development task but has no task type.
   Use: /new-feature [name] / /fix / /refactor / /hotfix / /edit-feature"
```

### What It Does NOT Flag

These are always allowed through without warnings:

| Type | Examples |
|---|---|
| Short messages (<6 words) | "ok", "yes", "go ahead", "phase 1" |
| Continuation words | "ok", "okay", "approved", "proceed", "next", "lgtm", "done" |
| Phase requests | "phase 1", "start phase 1 and 2", "develop", "all" |
| Questions | "what does this function do?" |
| Non-task requests | "explain the architecture", "review this code" |

### Warn Mode vs Block Mode

The hook ships in **warn mode** by default — Claude receives the advisory as context but the developer's message still goes through.

To switch to **block mode** (team enforcement — message does not reach Claude without classification):

```bash
# In .claude/hooks/require-task-type.sh
# Find the last exit 0 and change to exit 1

# Current (warn mode):
exit 0   # at the bottom of the WARN=1 branch

# Block mode:
exit 1   # message is rejected — developer must reclassify
```

**Recommendation:** Start with warn mode during adoption. Switch to block once the team is comfortable with the 5 commands.

```
        │

        │
        ▼

  → Claude calls EnterPlanMode (file writes now blocked at tool level)
        │
        ▼
GATE 1: requirements preview in chat
  Developer: "change acceptance criteria 2"
  → Claude updates content, shows again
  Developer: "ok"
        │
        ▼
GATE 2: design preview in chat
  Developer: "ok"
        │
        ▼
GATE 3: tasks preview in chat
  Developer: "ok"
        │
        ▼
Claude calls ExitPlanMode
  → writes specs/dark-mode/requirements.md
  → writes specs/dark-mode/design.md
  → writes specs/dark-mode/tasks.md
        │
        ▼

        │
        ▼

  → PreToolUse hooks fire (secrets check, spec check, protect-files)

        ▼

  → same hooks fire
        │
        ▼
"Phase 1 and 2 complete. tasks.md updated. Continue with phase 3?"
```

## Plan Mode — How It Works Mechanically

Plan mode (`EnterPlanMode`) is a Claude Code tool that prevents Claude from calling any file-write tools (`Write`, `Edit`, `Bash`). It is not a suggestion — it is enforced at the tool level.

**In plan mode Claude can:**
- Read files
- Show content as markdown text in the chat
- Have a conversation

**In plan mode Claude cannot:**
- Call `Write` to create spec files
- Call `Edit` to modify any file
- Call `Bash` to run commands
- Take any action that changes the filesystem

This is why `/new-feature` and `/edit-feature` use plan mode. The developer reviews all 3 spec documents before a single file is created. When the developer says "ok" at Gate 3, Claude calls `ExitPlanMode` and only then writes the spec files.

**Why not all 5 commands?**
- `/fix`, `/refactor`, `/hotfix` do not need it. These are fast paths where writing immediately after reading is the correct behaviour. Their enforcement comes from reading-before-writing rules and the approval gates within each command.

## Command vs ## Task Type — When to Use Each

| Situation | Use |
|---|---|
| Normal daily development | `/new-feature`, `/fix`, `/refactor`, `/hotfix`, `/edit-feature` |
| Automated pipeline / CI prompt injection | `## Task Type: New Feature` (see Prompt Guide) |
| Monorepo with package targeting | `## Task Type: New Feature` + `## Package:` header |
| Resume a previous session | `continue` or `## Task Type: New Feature (Resume)` |
| Project health check | `/audit` |

## FAQ

**Q: What if I forget the feature name?**
Just type `/new-feature` — Claude will ask "What is the feature name?"

**Q: Can I skip a gate and go straight to tasks?**
No. Gates are sequential by design. Requirements → Design → Tasks is the order. Design decisions depend on requirements. Task phases depend on the design layer breakdown.

**Q: What if I approved Gate 1 but want to change something in requirements after seeing the design?**
Tell Claude: "Go back to requirements — I need to change X." Claude will show the updated requirements again. You can iterate any gate as many times as needed before advancing.

**Q: Can I implement just Phase 3 without Phases 1 and 2?**
Claude will warn that Phase 3 depends on Phase 2. If you're adding Phase 3 to an already-implemented feature, use `/edit-feature` instead.

**Q: Does the require-task-type hook fire on every single message?**
Yes, but it only warns when a message contains specific development task keyword patterns. Short messages, continuation words, and questions pass through silently.

**Q: How do I switch require-task-type to block mode?**
Edit `.claude/hooks/require-task-type.sh` — find the last `exit 0` inside the `WARN=1` branch and change it to `exit 1`. The comment in the file explains exactly where.

**Q: What if ai-gov init generates new command files that overwrite my customisations?**
The commands in `.claude/commands/` use the same conflict-mode as all other generated files: `ask` mode will prompt you before overwriting. Use `--dry-run` first to see what would change.

**Q: Can I add my own slash commands?**
Yes. Create any `.md` file in `.claude/commands/` — it becomes a slash command immediately. Do not prefix with `ai-gov` to avoid conflicts with future updates.
