# AI Governance Upgrade Guide

**Version:** 17.2.0
**Command:** `ai-gov upgrade`

This guide covers how to upgrade an existing project from an older ai-gov version to the latest hooks, commands, and steering files — without losing your team's customised content.

---

## The problem: why you need upgrade

When you ran `ai-gov init` on your project six months ago, it generated hooks, commands, and steering files. Since then:

- Hook scripts have been updated (new checks, bug fixes, runtime improvements)
- Commands have new workflow gates
- CLAUDE.md has updated embedded rules
- Your team has customised `architecture.md`, `workflow.md`, and `coding-standards.md`

You want the new hooks and commands. You do not want to lose the team customisations. `ai-gov upgrade` handles this split.

---

## What gets upgraded vs what is preserved

| Path | Default behaviour | With `--force` |
|------|-------------------|---------------|
| `.claude/hooks/` (11 scripts) | Always regenerated | Always regenerated |
| `.claude/git-hooks/` (pre-commit.sh + 6 checks) | Always regenerated | Always regenerated |
| `.claude/commands/` (7 slash commands) | Always regenerated | Always regenerated |
| `.claude/CLAUDE.md` | Always regenerated | Always regenerated |
| `.claude/steering/architecture.md` | **Preserved** | Overwritten |
| `.claude/steering/coding-standards.md` | **Preserved** | Overwritten |
| `.claude/steering/workflow.md` | **Preserved** | Overwritten |
| `.claude/steering/constitution.md` | **Preserved** | Overwritten |
| `specs/` | Never touched | Never touched |

The four steering files contain your team's decisions about architecture patterns, naming conventions, and process rules. The upgrade command reads the existing `.claude/CLAUDE.md` to extract your app name and description, so the regenerated CLAUDE.md still references your project correctly.

## Step-by-step upgrade

### Step 1 — Check what you have

```bash
npx ai-gov doctor
```

This shows what is installed, whether python3/jq is available, and the current hook version. Take note of any warnings.

### Step 2 — Preview what would change

```bash
npx ai-gov upgrade --dry-run
```

Output shows each file that would be written. Nothing is touched in dry-run mode.

### Step 3 — Run the upgrade

```bash
npx ai-gov upgrade
```

This regenerates hooks, git-hooks, commands, and CLAUDE.md. Steering files are left exactly as they are.

### Step 4 — Review CLAUDE.md if needed

The regenerated `.claude/CLAUDE.md` contains your app name (extracted from the old CLAUDE.md or `package.json`). Open it and confirm the app name and description look correct before committing.

### Step 5 — Commit and push

```bash
git add .claude/   # or .kiro/ if using Kiro
git commit -m "chore: upgrade ai-gov hooks to v17.2.0"
git push
```

All teammates get the updated hooks and commands automatically on their next `git pull`. Each developer does not need to re-run any command — the scripts are in `.claude/` which is committed.

> **Exception:** If a developer has never run `ai-gov init --git-hooks` on their machine, their local `.git/hooks/pre-commit` wrapper does not exist. They need to run it once: `npx ai-gov init --git-hooks`.

## Upgrading steering files too (--force)

Use `--force` when the framework's architectural guidance has materially changed and you want to see the new baseline, then manually merge in your customisations.

```bash
# First: back up your current steering files
cp -r .claude/steering .claude/steering-backup

# Run force upgrade
npx ai-gov upgrade --force

# Open each file and manually re-apply your team's customisations
# The backup is in .claude/steering-backup/
```

Typical workflow: look at the diff between the generated file and your backup, and cherry-pick the new boilerplate improvements while keeping your team's decisions.

## Upgrading a specific directory

```bash
# Upgrade a specific project (not the current directory)
npx ai-gov upgrade --dir ./backend/api

# Override stack detection (useful if detection is wrong)
npx ai-gov upgrade --dir ./backend/api --stack java
```

## Upgrading a workspace (multiple projects)

For a workspace with multiple sub-projects, upgrade each project individually:

```bash
npx ai-gov upgrade --dir ./backend/api
npx ai-gov upgrade --dir ./backend/corp-node
npx ai-gov upgrade --dir ./frontend/corp-angular
```

Or write a small shell loop:

```bash
for dir in backend/* frontend/*; do
    if [ -d "$dir/.claude" ]; then
        echo "Upgrading $dir..."
        npx ai-gov upgrade --dir "$dir"
    fi
done
```

The workspace root's `.claude/` (steering, CLAUDE.md) is separate from per-project governance. The workspace root is typically not re-generated by upgrade — only per-project dirs that have their own `.claude/CLAUDE.md`.

## Troubleshooting

### "`.claude/` not found — run `ai-gov init` first"

Upgrade requires an existing `.claude/` directory. If the project has never been initialised:

```bash
npx ai-gov init
```

### App name is wrong after upgrade

Upgrade reads the app name from the existing `.claude/CLAUDE.md` using the pattern `**App:** <name>`. If that line does not exist (the CLAUDE.md was heavily customised), it falls back to `package.json`, `pom.xml`, or `pubspec.yaml`.

To force a specific name, edit `.claude/CLAUDE.md` after upgrade and update the `**App:**` line.

### Hooks still old after upgrade

Upgrade writes to `.claude/hooks/`. If your team members are still running old hooks, they need to do a `git pull` to get the updated scripts. No machine-level reinstall is needed.

### `--force` overwrote steering files accidentally

Restore from git:

```bash
git checkout HEAD -- .claude/steering/
```

This is why steering files are preserved by default.

## What changed in v17.0.0

### Kiro agent support

`ai-gov init --agent kiro` generates governance files in `.kiro/` with Kiro-native formats: steering files with YAML front-matter, JSON hooks auto-discovered by the IDE, and spec templates in `.kiro/specs/_template/`.

**Impact:** Teams using Kiro can now use the same governance framework. The `--agent` flag is available on `init`, `workspace`, `upgrade`, and `doctor`.

### Agent auto-detection

The CLI detects which agent to target from existing `.kiro/` or `.claude/` directories. No `--agent` flag needed if you already have governance set up.

### Workflow shortcuts (userTriggered hooks)

6 new `userTriggered` hooks provide the Kiro equivalent of Claude Code's slash commands: audit, new-feature, fix, refactor, hotfix, explore. Triggered from the Agent Hooks panel.

### Pre-write secrets gate

New `preToolUse` hook catches hardcoded credentials BEFORE they are written to disk — closes the enforcement gap where secrets were only detected post-write.

### Agent registry

Internal architecture change: agents are now registered in a central registry (`src/agents/types.ts`). Adding a third agent is a 3-line change.

## What changed in v16.0.0

### Python3 fallback for all hooks

Previously all bash hook scripts required `jq`. If `jq` was not installed, hooks silently did nothing — no errors, no warnings, no enforcement. This was a silent governance failure on most developer machines (macOS has python3 built-in but not jq).

v16.0.0 adds a `_json()` helper function to every Claude Code hook and a `cfg()` function to every git hook. Both try `jq` first and fall back to `python3`. When neither is available, the hook prints a visible warning to stderr and exits 0 instead of silently passing.

**Impact:** After upgrading, governance hooks are enforced on macOS out of the box without installing jq.

### Multi-repo workspace git hook installation

`ai-gov workspace` now detects whether each sub-project has its own `.git/` directory. For multi-repo layouts (each project is an independent git repo), it installs `.git/hooks/pre-commit` and `.git/hooks/commit-msg` wrappers automatically. For monorepo layouts, it installs one workspace-level hook at the root `.git/`.

### `ai-gov upgrade` command (new)

New command for safe, incremental upgrades without re-running full init. See this guide.

### Integration test suite (new)

v16.0.0 adds `tests/integration.test.ts` which executes generated bash scripts against real git repos. This catches shell-level bugs (like the python3 double-quote quoting issue) that unit tests of TypeScript generators cannot catch.
